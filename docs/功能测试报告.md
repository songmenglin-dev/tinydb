### v0.3-wire 修复（关键）

旧 v0.3 server 对 `SELECT id, name FROM t` 返回占位列名 `col0`/`col1`，导致：
- 上层 MyBatis 映射需显式 `@Results(column="col0", property="id")` 桥接
- Python Client `result.columns` 拿到的是 `["col0","col1"]` 而非 `["id","name"]`
- 与 v0.1 POLISH-CLI 修过的列名行为出现回归

**v0.3-wire 修复后**（commit `42775a9` + `1a1a37b`）：

```
$ python -c "
from tinydb.client import Client
c = Client('127.0.0.1', <port>, ...)
c.execute('CREATE TABLE t (id INT PRIMARY KEY, name TEXT, age INT)')
c.execute(\"INSERT INTO t VALUES (1, 'alice', 30), (2, 'bob', 25)\")
r = c.execute('SELECT id, name, age FROM t ORDER BY id')
print(r.columns)   # ['id', 'name', 'age']  ✓ 真实列名
print(r.rows)      # [[1, 'alice', 30], [2, 'bob', 25]]
"
```

**验证**:
- `tests/client/test_sync.py` `TestClientExecute` 和 `TestClientSqlPath` 的两处 `assert result.columns == ["id","name"]` 通过
- `tests/integration/jdbc-springboot/.../UserMapper.java` 删除 `@Results` 桥接后，Spring Boot + MyBatis 集成测试仍通过
- JDBC 端通过 `ResultSetMetaData.getColumnName(i)` 拿到 `id` / `name` / `age`（详见 §十五）

## 十七、v0.3-wire 引入并本次修复的回归

### 问题

commit `fd11696`（"fix(jdbc): wire-protocol LEN semantics match Python implementation"）把 Java driver 的
Frame LEN 语义从「payload + 2（含 type/flags）」改成「payload only」，与 Python server 对齐。
同时更新了 `CodecTest` / `FrameTest` / `MessagesTest` 的断言，但**遗漏了 5 个 fake-server
测试 helper**（`TinyStatementTest` / `TinyPreparedStatementTest` / `TinyConnectionTest` /
`TinyDatabaseMetaDataTest` / `StubCoverageTest`）。

具体表现：测试 fake server 用旧的 `len = payload.length + 2` 构造 Frame，调用 `Frame.write()` 时
新的 `len == payload.length` 校验抛 IOException，被外层 `catch (IOException) { /* ignore */ }`
吞掉，连接静默关闭。客户端 `Frame.read()` 拿到 null → 抛 "connection closed during handshake"。

### 影响范围（修复前）

```
mvn -f jdbc/pom.xml test
Tests run: 174, Failures: 2, Errors: 73, Skipped: 11                [FAIL]
```

73 errors + 2 failures 全部源于 fake-server 帧构造用了过时的 LEN 语义，外加 3 个独立的陈旧断言
（`setReadOnly` / `isReadOnly` / `getTransactionIsolation` / `getWarnings` / `clearWarnings` /
`getType` / `setNetworkTimeout` / `getNetworkTimeout` 在生产代码中已被故意改成「接受/返回默认」
以兼容 HikariCP/Spring 探测，但 `StubCoverageTest` 仍断言它们抛 SQLException）。

### 本次修复

| 文件 | 修改 |
|---|---|
| `jdbc/src/test/.../TinyStatementTest.java` | 4 处 `len = x.length + 2` → `len = x.length` |
| `jdbc/src/test/.../TinyPreparedStatementTest.java` | 3 处同上 |
| `jdbc/src/test/.../TinyConnectionTest.java` | 3 处同上 |
| `jdbc/src/test/.../TinyDatabaseMetaDataTest.java` | 4 处同上 |
| `jdbc/src/test/.../StubCoverageTest.java` | 3 处同上 + 移除 8 条针对故意增强方法的过期断言 |
| `jdbc/src/test/.../FrameTest.java` | `testBigEndianLength` 期望 LEN=0（空 payload）而非 0x02 |
| `jdbc/src/test/.../StubCoverageTest.java` | 移除/注释针对 `setReadOnly` / `isReadOnly` / `getTransactionIsolation` / `getWarnings` / `clearWarnings` / `getType` / `setNetworkTimeout` / `getNetworkTimeout` 的过期断言 |

修复后：

```
mvn -f jdbc/pom.xml test
Tests run: 174, Failures: 0, Errors: 0, Skipped: 11                [PASS]
```

> **回归保护**：所有 17 处 fake-server 帧构造现在用 payload-only LEN 语义，与 Python server
> 和生产 driver 一致。如果未来协议再次调整 LEN，单测会立刻失败。

## 二十、已知 Spec Gap（v0.3.1 待修复）

| Spec | 描述 | 现状 | 跟踪 |

| REQ-PROTO-4 | `QUERY SELECT 1`（无 FROM 子句）应返回 1 列 + 1 行 | parser 强制要求 FROM | parser 扩展 |

| CLI 多语句 | `-c "A; B"` 当前报 trailing token | parser 不接受 `;` 分隔 | parser 接受 `;` |
| JDBC @Disabled | savepoint / cursor / SQLXML | 11 个 skipped | v0.4 实现 |
